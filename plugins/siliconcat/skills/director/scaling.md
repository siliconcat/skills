# Scaling past one director

Read this when a request needs many rounds, a project passes about eight roles, or a build is too big for one session.

- **Request Manager**, the one extra layer. When a request needs many rounds (several build and verify cycles, a long bug hunt) that would flood your context, give it to a manager: a directing role with `Agent` in its tools that staffs that one request, records its workers with `req worker`, and reports to you at milestones. Its workers report to it; you talk to the manager. Subagents nest up to three layers below the main conversation by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), so a manager's workers can't spawn further.
- **Departments.** When a project passes about eight roles, propose grouping some behind a department director for one area. Its brief gives it the path of this skill's `SKILL.md` and tells it to run it scoped to its area and roles (the skill is user-invoked, so it can't load it by name). It reports to you.
- **A build too big for one session** (a new app, a large feature): plan it into slices that each fit one fresh context before staffing it. If the user has Matt Pocock's planning skills installed, suggest them (`/wayfinder` for a foggy effort, `/to-spec` then `/to-tickets` for a clear one); they are user-invoked, so only the user can start them. Otherwise plan the slices with the user directly. Then a Request Manager works the tickets as a queue (`queue.md`), or the user runs `/implement-spec` in its own session. The structure goes into the tickets, not into more layers of agents.
